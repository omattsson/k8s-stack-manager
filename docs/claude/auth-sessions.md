# Sessions and WebSocket Auth

Reference for Claude Code and other agents. The root `CLAUDE.md` links here. Read this file before you work in this area.

**Sessions.**
- Login returns a JWT (with a `jti` and a `sid` session claim) and a refresh token.
- `POST /auth/refresh` rotates the refresh token through `RefreshTokenRepository`. Each login starts a session family (`family_id`, `session_started_at`).
- A rotated token that comes again within `REFRESH_REUSE_GRACE` (default 30s, for concurrent tabs) gets a new access token and no new cookie. Later reuse revokes the family.
- The idle limit (`SESSION_IDLE_TIMEOUT`, default 30m) counts from the last authenticated request. The JWT middleware touches the `last_activity` of the family, at most one write for each session per interval: a quarter of `SESSION_IDLE_TIMEOUT`, at most 1 minute and at least 1 second (`middleware.SessionActivityInterval`). So a session can count as idle about one interval before the full timeout after its last request.
- `SESSION_MAX_LIFETIME` (default 12h) caps a session. Rotation never extends it.
- Exceptions: the SSO CLI token has no session and lives for `JWT_EXPIRATION`. API keys have no session. `/ws` traffic is not activity.
- `/auth/logout` ends the sessions that the request proves (#699): the family of the refresh token cookie (`RevokeFamilyForUser` when the credential names the user, else `RevokeFamily`; the whole family, so the active successor of a rotated token is revoked too, #673) and the `sid` of a valid bearer token, also without the cookie. When they differ, both end: each credential alone could end its session, so this gives no new power. Then it blocks each session (`BlockSessions`), blocklists the `jti` of the access token and closes its sockets. The order is revoke, then block: a refresh whose session recheck passed before the revoke signed its token before the block, and the block covers it. A failed lookup or revoke still blocks, clears the cookie and closes the sockets, but answers 500. No cookie and no valid bearer token: nothing to end, 200.
- The session block (`sessionstore` kind `session_block`, no migration) is a plain block, not based on the issue time. It lasts `AccessTokenExpiration` plus 1 minute, the latest expiry of an access token of the session. So after a logout, every access token of the session gets 401 and its sockets close, and other sessions of the user keep working. When the family revoke failed (logout or replay), the block lasts until `SESSION_MAX_LIFETIME` plus the margin instead, because the refresh token still works. `POST /auth/refresh` reads the block (`IsSessionBlocked`, also in the reuse grace path): a blocked family gets 401 "Session revoked", is revoked best effort and loses its cookie; a store error fails open. A second block keeps the later expiry. A replay of a rotated refresh token (family revoke) blocks the session too. Normal expiry (idle or maximum lifetime) does not.
- `/auth/logout-all` revokes every refresh token of the user, then lists the recent session families (`ListRecentFamiliesForUser`: refresh-token rows of the user that expire after now minus the access token lifetime, the 1 minute block margin and `REFRESH_REUSE_GRACE`; revoked rows included, because a family revoked by idle timeout or the token cap can still hold a live access token; newest first, at most 1000, a warning when the limit is hit; a legacy row is its own family), adds the `sid` of the presented token, and blocks every listed session (`BlockSessions`: normal block, the long block for each when the revoke failed; on MySQL one multi-row upsert per 500 sessions, and a failed later batch leaves the earlier blocks written). It then writes a user block (`BlockUser`, same lifetime rule as the user revoke), blocklists the `jti` and closes all sockets of the user. Access tokens issued before it are rejected. Every access token of a session with a row in that list is rejected while the replica clocks differ by less than the 1 minute block margin. The refresh-token cleanup keeps a row for that same window after it expires (it deletes rows that expired before now minus the window), so a session that can still hold a live access token still has a listed row. A session without such a row relies on the user block: a login whose refresh-token create failed (it still hands out an access token with a `sid`). So does a token without a `sid` (the SSO CLI token). The user block holds on NTP-synchronised clocks: the user block compares the issue time with the block time and has no clock-skew margin on purpose (a margin would also reject a login right after the block, see `userBlockApplies`). A login afterwards (a new family) works, also one that commits after the listing. The session blocks, the user block and the socket close run even when the revoke fails (500); a refresh of a session whose revoke failed gets 401 "Session revoked". When only the listing fails (logged), the revoke and the user block still run and the answer is 200 if the revoke succeeded. When the listing and the revoke both fail, only the presented session is blocked and the other sessions stay refreshable (500); there is no second listing attempt (the database is most likely down, and with the default MySQL session store the session store shares it).
- Rolling update: replicas of an older version do not read `session_block`. During a rollout a token of a logged-out session can pass on an old replica until it expires (as before #699). A session whose revoke failed (logout, replay or logout-all) can also still refresh on an old replica, because only its block covers it. A logout served by an old replica also does not revoke the `sid` family when the request has no cookie. The user block of logout-all is read by old replicas too. A leader of an older version runs the refresh-token cleanup at expiry, without the session window, so until the leader runs this version a session whose last row expired can be missing from the logout-all listing and relies on the user block, as before.
- JWT auth checks `IsTokenBlocked`, `IsSessionBlocked(ctx, sid)` (only for a token with a `sid`) and `IsUserBlocked(ctx, userID, issueTime)`.
  - A user block rejects only tokens issued at or before the block time (401).
  - The precision is one millisecond. Access tokens carry `iat_ms`. The block time is stored in ms. A legacy token without `iat_ms` keeps the rule "same second or before".
  - `BlockUser` writes two rows: `user_block` in seconds (older versions read it during a rolling update) and `user_block_ms`. See `userBlockTime` and `Claims.IssueTime`.
  - The check fails open on a store error (log and continue).
- API-key auth skips the blocklist.
- Delete, disable, password reset and role change revoke refresh tokens, then block earlier tokens (the block comes after the revoke, for the same refresh race as logout). Delete also removes the API keys. A role change keeps them, because API-key auth reads the current role.
- `MAX_REFRESH_TOKENS_PER_USER` (default 10) caps the active refresh tokens of a user at about that number. A new token revokes only the least recently used ones (issued or rotated; `RevokeOldestForUser`), never all of them: revoking all also killed the new session of a concurrent login (401 "Session revoked", #619). Concurrent logins can exceed the cap by up to N-1 until the next token is issued.
- Every failed login writes one log line `Login failed` with a fixed `reason` (`user_not_found`, `password_mismatch`, `no_password` (a user without a local password, for example an SSO user; status `invalid`), `hash_invalid` (only a malformed stored hash), `hash_changed`, `session_revoked`, `disabled`, `lookup_error`, ...), the username, `cache_hit`, `client_ip` and `request_id`, and `auth.login.total` gets the `reason` label (`handlers/login_failure.go`). Never the password, hash or token. The client keeps the generic 401; a database error gives 500, not 401.
- Login checks the password before the account state (#632). An unknown user, or a user without a usable hash, runs one bcrypt compare against a dummy hash (`dummyPasswordHash`, cost `passwordHashCost`). Without the correct password, every case gets the same 401 "Invalid username or password". "Account disabled" (403) and the SSO-only 403 come only after a correct password.
- A login cache hit (`LOGIN_CACHE_TTL`) skips only bcrypt. After the password check, the login reads the user again and uses that record (disabled check, token role). A changed password hash gives 401.
- All auth paths (login, refresh, OIDC, API key) reject `User.Disabled`.
- Register (`POST /auth/register`) needs an admin, or `SELF_REGISTRATION=true` (code and Helm chart default `false`; Docker Compose sets `true` for development).
- WebSocket auth:
  - The `/ws` upgrade accepts a JWT in the `Sec-WebSocket-Protocol: bearer, <jwt>` subprotocol, in the `Authorization` header or in `?token=`. It accepts an API key in the `X-API-Key` header only.
  - It runs the same checks (`middleware.CheckRevocation`, fail open) and also rejects a deleted or disabled user (401). A user lookup error gives 500.
  - An API-key upgrade counts against the per-IP API rate limit.
- WebSocket revocation:
  - The hub (`websocket.ClientRevoker`) closes sockets with code 1008 on delete, disable, password reset, role change and logout-all (`DisconnectUser`), on logout (`DisconnectToken`) and on API key delete (`DisconnectAPIKey`).
  - The upgrade and the revalidation also reject a token of a blocked session (`sid`, `ClientIdentity.SessionID`), so the sockets of other access tokens of a logged-out session close within the revalidation interval.
  - Each socket also closes when its access token (or API key) expires.
  - The frontend reconnects. It refreshes the token first after a 1008 close or near expiry. A refresh is not idle activity: the rotated refresh token keeps `LastActivity`.
  - With fan-out, a revocation reaches the other replicas through `ws_events` within about one poll interval.
  - `Hub.StartRevalidation` re-checks all open sockets every minute (fail open). It closes sockets that a direct database change or a blocklist entry made invalid.
