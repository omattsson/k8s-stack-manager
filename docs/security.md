# Security model

The security controls of the application. The roles (`user`, `devops`, `admin`) are in the [README](../README.md#roles-and-security-model). The security values of the Helm chart are in [Deployment](deployment.md#security-settings-of-the-chart). See the [README](../README.md) for an overview and the [documentation map](../README.md#documentation).

- **Instance access.** Only the owner, `admin` users, and `devops` users can change or operate an instance. Other users see it read-only. See [Stack instance permissions](../WIKI.md#stack-instance-permissions).
- **Definition access.** Only `devops` and `admin` users can create or import a definition, and add or remove charts. A user without these roles cannot change the chart name, repository, path, or version. The owner, `devops`, and `admin` can change or delete a definition.
- **Chart source allowlist.** Helm installs charts with the identity of the backend. Set `ALLOWED_CHART_REPOS` (Helm value `backend.allowedChartRepos`) to a list of chart repository URL prefixes. The backend then rejects all other chart sources when a chart config is saved and again at deploy time. An empty list allows every chart source. Set the list on every cluster that untrusted users can deploy to. See [Chart sources](../WIKI.md#chart-sources).
- **Image digest lookups.** The `imageDigest` values template function contacts only the registry of the target cluster and the hosts in `IMAGE_DIGEST_REGISTRIES` (Helm value `backend.imageDigestRegistries`), so a value override cannot make the backend call another host. Only the cluster registry gets the cluster registry credentials. List only registries that you trust.
  - Any user who can deploy or preview an instance can learn through the lookups which repositories and tags exist on the cluster registry, with the cluster credentials (an empty digest means that the tag was not found or the lookup failed). This is accepted: the cluster pulls the images of every deploy with the same credentials, so a user who can deploy can already make the cluster pull any image of that registry.
  - A registry may redirect a lookup or name a token server on another host. When that host is not allowed, the backend refuses it when the host name resolves to a loopback, private (RFC 1918, IPv6 ULA), link-local, CGNAT (100.64.0.0/10), 0.0.0.0/8 or unspecified address. The check runs on the resolved address when the connection is made, so a DNS name that changes its answer (DNS rebinding) cannot pass it. The allowed hosts may have private addresses (internal registries). Limit: with an HTTP proxy (`HTTPS_PROXY`), the backend connects to the proxy and the proxy resolves the target name, so the backend cannot check the target address. When you set a proxy for the backend, the proxy must refuse internal targets (loopback, private, link-local and CGNAT addresses, the cloud metadata address 169.254.169.254, and the cluster service network); otherwise a registry redirect can reach them through the proxy. The backend skips the check only for the exact proxy address (host and port); another port of the proxy host is checked. IPv6 addresses that carry an IPv4 address (IPv4-mapped, IPv4-compatible, NAT64 `64:ff9b::/96`, 6to4 `2002::/16`) are checked by that IPv4 address; the local-use NAT64 prefix `64:ff9b:1::/48` is refused.
- **Namespace-scoped RBAC.** With `backend.rbac.scope: namespace` (default), the Helm chart gives the backend namespaced rights only inside stack namespaces. A stack chart cannot read or change objects in other namespaces, and cannot create cluster-scoped objects. A ValidatingAdmissionPolicy (Kubernetes 1.30 or later) keeps the backend inside stack namespaces. See [Backend rights on the cluster](../WIKI.md#backend-rights-on-the-cluster).
- **Port-forward.** Off by default. A tunnel needs `STACK_PORT_FORWARD_ENABLED` (Helm `backend.portForward.enabled`) and the cluster switch `allow_port_forward` (admin, off by default). The backend refuses namespaces without the label `managed-by=k8s-stack-manager` and its own namespace. A tunnel goes past NetworkPolicies and past the authentication of an ingress or SSO proxy in front of a tool. Keep the switch off on clusters with real data. See [Port-forward](../WIKI.md#port-forward).
- **Exec.** Off by default. A command needs `STACK_EXEC_ENABLED` (Helm `backend.exec.enabled`), the cluster switch `allow_exec` (admin, off by default) and a container name in `STACK_EXEC_ALLOWED_CONTAINERS`. Exec shows the container environment and its secrets: turn it on only where the stack owners may see them. A container that holds a service-account token is refused. See [Exec](../WIKI.md#exec).
- **Sessions and tokens.** Access tokens are short-lived. Refresh tokens rotate. You can revoke users and sessions. See [Sessions](../WIKI.md#sessions).
- **Secrets at rest.** Kubeconfig data, registry passwords, notification channel secrets, and (when the key is set) notification channel webhook URLs are encrypted with a key that the application derives from `KUBECONFIG_ENCRYPTION_KEY`. Without the key, the backend refuses kubeconfig data, registry passwords, and channel secrets. It stores webhook URLs in plaintext.
- **HTTP hardening.** The application sets security headers and rate limits, and has panic recovery. The Gin framework runs in release mode unless you set `APP_DEBUG=true` or `GIN_MODE`. The code default of `APP_DEBUG` is `true`; Docker Compose and the Helm chart set it to `false`.
- **Bundled MySQL.** Docker Compose and the Helm chart (`mysql.enabled`) run Oracle's upstream image `mysql:8.4.13`. On 2026-11-07 Trivy reported 2 CRITICAL and 33 HIGH findings in it. They come from the Python packages bundled with the MySQL Shell (certifi, cryptography, pyOpenSSL, urllib3) and from the `gosu` binary (Go standard library), not from the MySQL server. This project does not install these components and cannot patch them; only a new Oracle image can. CI scans the image for information and does not fail on it. For production, set `mysql.enabled=false` and use an external database.
- **Image scans.** The weekly Security Scan workflow builds the backend and frontend images and scans them with Trivy (amd64); it fails on a fixable CRITICAL or HIGH finding. To accept a finding that has no fix yet, add an entry to `.trivyignore`: a `#` comment line with the reason and the upstream package, then the CVE ID with an `exp:YYYY-MM-DD` date at most 90 days away. `scripts/check-trivyignore.sh` checks the entries in the same workflow.

Note: The Helm chart sets `CORS_ALLOWED_ORIGINS` to `same-origin`: only the web UI on the ingress host can call the API from a browser. The code default is `*` (all origins) for local development; the backend logs a warning for `*` when `GO_ENV=production`.
